# RQ8 — What do winning open standards share vs losers?

Research notes: adoption physics of data/serialization/web standards. Winners (JSON, HTTP/HTML, CSV), losers/stalls (XHTML 2.0, XML-for-data, YAML's curse, S-expressions), modest win (TOML), plus the "worse is better" lens and JSON-vs-XML displacement data.
Method: web research, 2026-07-14. Unverifiable claims flagged UNVERIFIED; weak sourcing noted inline.

---

## WINNERS

## 1. JSON — "discovered, not invented"

### Origin
- First JSON message: April 2001, sent by Douglas Crockford and Chip Morningstar (State Software) from a Bay Area garage — it was literally a JavaScript object literal smuggled inside an HTML frame, because they needed cross-browser data passing that worked in both IE and Netscape 4. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
- Quoted keys exist because of a bug: their first message used `do` as a key, which is a JavaScript reserved word. Rather than track 60+ reserved words, Crockford mandated quoting all keys. Pragmatic patch → permanent grammar. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
- Crockford, verbatim: "I discovered JSON. I do not claim to have invented JSON, because it already existed in nature. What I did was I found it, I named it, I described how it was useful." He notes someone at Netscape was doing the same with JS array literals as early as 1996. [Source](https://nofluffjuststuff.com/blog/douglas_crockford/2008/01/the_discovery_of_json) [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
- 2002: Crockford buys json.org, posts the full grammar and a reference parser. Clients wouldn't adopt an unspecified format, so he wrote the world's shortest spec instead of a standards process. The entire grammar is six railroad diagrams; famously it also fits on the back of a business card (business-card claim: widely reported, e.g. [Source](https://www.merge-json-files.com/blog/when-json-was-invented-and-who-invented-it) — WEAKLY SOURCED but consistent with the json.org grammar's size). [Source](https://www.json.org/json-en.html) [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)

### Zero-config parsing + free distribution
- JSON's killer property: the parser was already installed on every computer on earth — "Since the message is just JavaScript, it doesn't require any kind of special parsing. The JavaScript interpreter can do it all." (eval() initially; native, safe `JSON.parse`/`JSON.stringify` landed in ECMAScript 5, 2009.) [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html) [Source](https://exploringjs.com/es5/ch22.html)
- 2005: Jesse James Garrett coins "AJAX"; in the follow-up Q&A he blesses JSON as an acceptable alternative to the X in AJAX. The AJAX boom becomes JSON's distribution rocket. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
- Deliberate feature subtraction: Crockford *removed comments* from JSON — "I removed comments from JSON because I saw people using them to hold parsing directives, a practice which would have destroyed interoperability." Only two changes ever (comments removed, scientific notation added, both 2005); the spec has been frozen since, and is not versioned. [Source](https://news.ycombinator.com/item?id=3912149) [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)
- Standards bodies arrived *after* victory to describe reality: ECMA-404 (2013), RFC 8259 (2017). Standardization ratified adoption; it did not cause it. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html) [Source](https://www.rfc-editor.org/rfc/rfc8259)
- Data-model fit: Crockford's stated advantage — JSON was designed as a *data interchange* format, while XML was a *document markup* language (SGML lineage, mixed content). JSON dropped documents entirely: just dicts and arrays, "the basic and familiar elements all programmers use." [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
- The famous exchange: Dave Winer (XML-RPC/RSS), Dec 2006: "Who did this travesty? Let's find a tree and string them up. Now." Crockford's reply in the comments: "The good thing about reinventing the wheel is that you can get a round one." [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)

## 2. HTTP/HTML — distribution via the browser, victory via forgiveness

- HTML processing runs on Postel's law ("be liberal in what you accept"): browsers "produce a reasonable result even in the presence of severe markup errors." The forgiving parser meant every amateur's broken page still rendered — authorship scaled with no gatekeeping. [Source](https://www.w3.org/html/wg/wiki/DraconianErrorHandling) [Source](https://en.wikipedia.org/wiki/Well-formed_document)
- The counterfactual was actually run (see XHTML 2.0 below): when the W3C tried to replace forgiving HTML with draconian XML-validating documents, the installed base refused, and the browser vendors defected. [Source](https://wiki.whatwg.org/wiki/W3C)
- HTML5's written design principles — "Support Existing Content," "Degrade Gracefully," "Pave the Cowpaths," "Evolution, not Revolution" — are the codified adoption physics of the whole web platform. [Source](https://html5forwebdesigners.com/design/)
- Lesson pairing with JSON: both winners had a universal client pre-installed (the browser) and zero cost of partial adoption. (Synthesis.)

## 3. CSV — ubiquity without a spec for ~30 years

- RFC 4180 (Yakov Shafranovich, October 2005) opens by admitting the format it "standardizes" long predates it: CSV "has been used for exchanging and converting data between various spreadsheet programs for quite some time," yet "it has never been formally documented." The RFC is descriptive, registering `text/csv` and writing down observed practice. [Source](https://www.rfc-editor.org/rfc/rfc4180.html)
- CSV-like list-directed I/O goes back to early-1970s Fortran; the format spread as the least-common-denominator export of every spreadsheet (VisiCalc → Lotus → Excel). Early-Fortran claim per Wikipedia's history section — WEAKLY SOURCED beyond that. [Source](https://en.wikipedia.org/wiki/Comma-separated_values)
- CSV's winner profile: the "parser" is split-on-comma (good enough for 90% of files), the killer app was the spreadsheet (pre-installed on every office computer), and there was no consortium, no version, no validator. It also shows the cost of that path: quoting/escaping/encoding chaos that RFC 4180 could only partially tame, and dialect hell (delimiters, headers, encodings) that persists today. [Source](https://www.rfc-editor.org/rfc/rfc4180.html) [Source](https://fastcsv.org/architecture/interpretation/)

## LOSERS AND STALLS

## 4. XHTML 2.0 — the canonical backward-compatibility corpse

- XHTML 2.0 was explicitly designed *not* to be backward compatible with HTML/XHTML 1.x; W3C direction circa 2000–2004 was new, cleaner markup (XForms, XHTML 2.0) rather than evolving HTML. [Source](https://en.wikipedia.org/wiki/XHTML) [Source](https://wiki.whatwg.org/wiki/W3C)
- June 2004, W3C Workshop on Web Applications and Compound Documents: Mozilla and Opera jointly proposed evolving HTML backward-compatibly; the W3C membership voted the proposal down. Apple, Mozilla, and Opera formed WHATWG days later to build what became HTML5 outside the W3C. [Source](https://wiki.whatwg.org/wiki/W3C) [Source](https://en.wikipedia.org/wiki/WHATWG)
- XHTML 2.0 additionally required XML's draconian error handling on the public web (yellow-screen-of-death on any error), which the deployed corpus of broken HTML could never satisfy: "too many websites depended on HTML's forgiving rules." [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html) [Source](https://www.oreilly.com/library/view/html5-up-and/9781449392154/ch01s06.html)
- July 2009: W3C announced it would let the XHTML 2 Working Group charter expire at end of 2009 and reallocate resources to HTML5. Zero major-browser implementations, ever. [Source](https://www.sitepoint.com/rip-xhtml-2/) [Source](https://brucelawson.co.uk/2009/goodbye-xhtml-2/)
- Historical verdict (twobithistory): "I read the failure of XHTML as a kind of moral defeat for the XML camp. If XML wasn't the best tool for HTML, then maybe there were better tools out there for other applications also." The XHTML defeat presaged XML's data-plane defeat by JSON. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)

## 5. XML-for-data — over-generalization and the schema-industrial complex

- Category error at birth: XML descends from SGML (document markup, mixed content, "editor with a red pen" metaphor) but was marketed as the universal *data* format. Crockford's core critique: JSON was designed for data interchange; XML wasn't. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
- Verbosity: "the angle bracket tax" (Atwood) — every open tag needs a closing tag; documents carry heavy redundancy, hurting both size and human scanning. [Source](https://blog.codinghorror.com/xml-the-angle-bracket-tax/)
- The attribute-vs-element ambiguity: XML gives two ways to encode every field (`<a b="c">` vs `<a><b>c</b></a>`) with no principled rule — a permanent modeling debate JSON simply doesn't have. (Long-running community debate; canonical statements are scattered — MODERATELY SOURCED.) [Source](https://www.ibm.com/docs/en/integration-bus/10.0?topic=model-xml-attributes-vs-elements) 
- Draconian error handling: XML 1.0 (1998) mandates fatal errors on well-formedness violations. The 1997 SGML-WG debate that produced this ("Draconians" — Tim Bray, Jon Bosak — vs "Tolerants") is archived; Bray later defended it as a reaction to the "intolerable results" of tag-soup HTML. It made XML safe for machines and hostile to casual authors. [Source](https://lists.w3.org/Archives/Public/w3c-sgml-wg/1997Apr/0164.html) [Source](https://www.tbray.org/ongoing/When/200x/2003/08/19/Draconianism)
- The schema-industrial complex: even XML's own co-editor turned on the tooling stack. Tim Bray, 2003: processing arbitrary XML in code is "irritating, time-consuming, and error-prone" ("XML Is Too Hard For Programmers"); and on W3C XML Schema (XSD): hard to read, hard to write, interop-hostile — "Choose RELAX Now." The ecosystem (XSD, XSLT, SOAP, WS-*) grew a consultancy layer that priced out casual users. [Source](http://www.tbray.org/ongoing/When/200x/2003/03/16/XML-Prog) [Source](http://www.tbray.org/ongoing/When/200x/2006/11/27/Choose-Relax)
- Displacement mechanics (see §9 for numbers): every browser shipped a free JSON parser (the JS engine); XML parsing in JS required DOM traversal ceremony. Twitter dropped XML from its API in 2013; of the ten most popular web APIs in 2017, only one was XML-first. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
- Where XML survives: document-shaped data — SVG, RSS/Atom, Android manifests, office formats. It lost *data interchange*, not *documents*. [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)

## 6. YAML — adopted but cursed

- Adoption vector was infrastructure tooling, not merit-in-isolation: Ansible, Docker Compose, Kubernetes manifests, GitHub Actions, Helm — YAML became "the language of infrastructure." Its human-friendliness + comments made it the only viable config option for years: "we need comments, which rules out json... for a long time it was the only viable configuration format." [Source](https://thenewstack.io/yall-against-my-lingo-why-everyone-hates-on-yaml/) [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)
- Spec complexity, primary-sourced: the YAML 1.2.2 spec is 10 chapters with four-level-deep section numbering and a dedicated errata page; PEP 518 measured the spec at "86 pages if printed on letter-sized paper" when rejecting YAML for pyproject. Versions matter: the same document parses differently under YAML 1.1 vs 1.2, and libyaml/PyYAML still implement 1.1 behavior. [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell) [Source](https://peps.python.org/pep-0518/)
- The Norway problem: in YAML 1.1, unquoted `no` parses as boolean `false` (likewise `on`/`off`/`yes`/`y`/`n`), so `geoblock_regions: [dk, fi, is, no, se]` yields `[..., false, ...]`. Canonical writeup: StrictYAML's "why implicit typing was removed." Related: `22:22` is a base-60 (sexagesimal!) literal in 1.1 → `1342`; unquoted `10.23` becomes a float; `on:` as a mapping key parses as `true` (GitHub Actions works around this). [Source](https://hitchdev.com/strictyaml/why/implicit-typing-removed/) [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)
- Multiline strings: a dedicated community website exists just to choose among YAML's multiline syntaxes; a widely-cited Stack Overflow answer counts 63 combinations. [Source](https://yaml-multiline.info/) [Source](https://stackoverflow.com/a/21699210/135889)
- Security: YAML tags can invoke arbitrary constructors — "loading an untrusted yaml document is generally unsafe" (hence PyYAML's safe_load). Billion-laughs via anchors/aliases is real and was weaponized: CVE-2019-11253 let a crafted ~kilobyte YAML manifest DoS the Kubernetes API server (fixed in 1.13.12/1.14.8/1.15.5/1.16.2). [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell) [Source](https://github.com/kubernetes/kubernetes/issues/83253)
- Governance contrast with JSON: YAML 1.2.2 (Oct 2021) took "years of work by the new YAML language development team," which "plans to actively evolve yaml, rather than to freeze it." JSON: frozen, unversioned, two changes ever. [Source](https://yaml.com/blog/2021-10/new-yaml-spec/) [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)
- Net lesson: YAML proves distribution can force adoption of a cursed format — and that "human-friendly" features (unquoted scalars, implicit typing) are precisely the footguns. Experienced users defensively quote everything, i.e., they manually re-impose the rigor the format removed. [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)

## 7. TOML — deliberately minimal, modest win

- Created by Tom Preston-Werner (GitHub co-founder), initial commit Feb 24, 2013; v1.0.0 released Jan 11, 2021. Stated goal, verbatim: "TOML aims to be a minimal configuration file format that's easy to read due to obvious semantics." Strings are always quoted — the direct anti-Norway design decision. [Source](https://en.wikipedia.org/wiki/TOML) [Source](https://toml.io/en/)
- Won by institutional selection, not virality: Rust's Cargo chose it (Cargo.toml); Python's PEP 518 chose it for pyproject.toml after explicitly rejecting JSON ("does not lend itself to easy editing... not allowing for comments"), YAML ("the specification is large: 86 pages"), and configparser ini (no standard, not flexible enough). PEP 518 also cited Cargo's happy experience. [Source](https://peps.python.org/pep-0518/)
- Ceiling: deeply nested data is awkward ("A weak spot of toml is deeply nested data"), so it stays a config format, not a general interchange format. Modest scope → modest, durable win. [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)

## 8. S-expressions — elegant, never escaped Lisp

- The most syntactically minimal structured format ever deployed (atoms + parens, homoiconic, trivially parseable) — and the clearest proof that elegance alone confers ~zero adoption force. (Framing synthesis; facts below.)
- Ron Rivest wrote an S-expression data-interchange spec in May 1997 (draft-rivest-sexp, for SPKI certificates, explicitly "more widely applicable"), including a canonical form for signing. It was never even formally submitted to the IETF at the time. [Source](https://datatracker.ietf.org/doc/html/draft-rivest-sexp-05) [Source](https://www.rfc-editor.org/rfc/rfc9804.pdf)
- It finally became RFC 9804 (Informational, Rivest & Eastlake) in **June 2025 — 28 years after the draft** — by which time its production users were roughly: GnuPG/libgcrypt internals, Nettle, lsh, Ribose RNP. [Source](https://datatracker.ietf.org/doc/rfc9804/) [Source](https://en.wikipedia.org/wiki/S-expression)
- Why they never escaped (analysis, flagged as such): (a) no host with distribution — Lisp itself was the only "browser" for sexprs, and Lisp was in decline ("worse is better" was literally written about this, §10); (b) no native mapping to the record/dict data model programmers wanted — everything is a list, so field access needs conventions (alists/plists) that were never standardized; (c) culture: parens read as "code," and non-Lisp programmers pattern-matched them as alien. Each sub-claim is inference from the adoption record, not directly sourced — UNVERIFIED as stated causes.
- Echo of the pattern: Rivest's canonical S-expressions solved (in 1997!) the canonicalization-for-signing problem JSON still struggles with (JCS, RFC 8785, arrived 2020) — being early and right didn't matter without a carrier. [Source](https://www.rfc-editor.org/rfc/rfc9804.pdf) [Source](https://www.rfc-editor.org/rfc/rfc8785)

## CROSS-CUTTING

## 9. JSON vs XML — the displacement data

- ProgrammableWeb directory data: XML peaked at **72.66% of all APIs in September 2009**; by May 2011, 1 in 5 *new* APIs were JSON-only ("1 in 5 APIs Say 'Bye XML'"), and JSON hit 51% of new APIs added March–April 2011. [Source](https://www.programmableweb.com/news/1-5-apis-say-bye-xml/2011/05/25) [Source](https://www.programmableweb.com/news/jsons-eight-year-convergence-xml/2013/12/26) (ProgrammableWeb shut down in 2023; links may need archive.org.)
- Twitter dropped XML entirely in its API v1.1 era (2013); by 2017, 9 of the 10 most popular web APIs were JSON-first. Stack Overflow question volume: JSON passed XML and became the most-asked-about interchange format (visible in SO Trends). [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html) [Source](https://insights.stackoverflow.com/trends?tags=json%2Cxml%2Cprotocol-buffers%2Cyaml%2Ccsv)
- Timeline shape: XML dominance 2000–2009 → crossover in new APIs ~2011 → JSON default by ~2013–2014 → near-total for new public APIs by the 2020s. The displacement took roughly a decade from JSON's spec (2002) to parity, driven by AJAX (2005) and mobile/REST (2008+). [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html) [Source](https://www.programmableweb.com/news/jsons-eight-year-convergence-xml/2013/12/26)

## 10. "Worse is better" (Richard Gabriel) as the lens

- Origin: Gabriel's 1989 essay (spread via his 1990 EuroPAL talk and the 1991 AI Expert publication of "Lisp: Good News, Bad News, How to Win Big"), contrasting the MIT approach ("the right thing": interface correctness/completeness first) with the New Jersey approach (implementation simplicity first). [Source](https://www.jwz.org/doc/worse-is-better.html) [Source](https://en.wikipedia.org/wiki/Worse_is_better)
- Core claim: "worse-is-better... has better survival characteristics than the-right-thing." The mechanism: simple-implementation software spreads like a "virus," conditions users to expect less, then gets improved to "90% of the right thing" — while the right thing is still being designed. [Source](https://www.jwz.org/doc/worse-is-better.html)
- Direct applications in this corpus: C/Unix over Lisp (Gabriel's own case); JSON over XML (simple implementation, no schema, no namespaces — improved later with JSON Schema/JCS); Markdown over reST/AsciiDoc; HTML5 over XHTML 2.0; CSV over everything. Werner Vogels explicitly invoked it for Markdown-vs-CommonMark in 2014. [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/)
- Caution: Gabriel himself oscillated for years about whether worse-is-better is *good* (he wrote rebuttals under a pseudonym, "Worse Is Better Is Worse"). The lens predicts adoption; it does not bless the outcome — YAML is worse-is-better gone septic. [Source](https://en.wikipedia.org/wiki/Worse_is_better) [Source](https://www.dreamsongs.com/WorseIsBetter.html)

## 11. Preconditions for a NEW format in 2026 (extraction)

Pattern across winners (JSON, HTML, CSV, Markdown, TOML) vs losers (XHTML2, XML-for-data, sexprs) — each precondition evidenced above:

1. **A killer distribution vehicle that pre-installs the parser.** Browser JS engine (JSON), the browser itself (HTML), the spreadsheet (CSV), GitHub/SO (Markdown), Cargo/pip (TOML). S-expressions and org-mode are the control group: superior formats with no carrier. In 2026 the analogous carriers are: LLM training corpora + agent runtimes + editor/IDE renderers.
2. **Zero-config, zero-dependency parsing.** If the reference parse isn't a weekend project, the format loses (JSON's six diagrams vs YAML's 86 pages vs XSD). Every format that required a toolchain to *begin* (DocBook, XML+XSD) stalled with casual users.
3. **Incremental adoption path / backward compatibility with the installed base.** HTML5's "Support Existing Content" vs XHTML2's clean break; GFM as strict superset of CommonMark; JSON as subset-of-JavaScript. A new format must be adoptable one file (or one block) at a time inside existing workflows.
4. **Escape hatches for the unspecified.** Markdown's inline HTML, HTML's unknown-element tolerance, TOML's string values. Formats that force everything into the blessed vocabulary (XHTML2, strict schemas) die at the first unmodeled need.
5. **Frozen core, extension at the edge.** JSON froze and won; YAML "actively evolves" and every document is version-ambiguous. Extensions must be syntactically self-announcing (GFM tables) rather than semantic reinterpretations of existing syntax (YAML 1.1→1.2 changing what `no` means).
6. **Descriptive standardization, late.** RFC 4180, ECMA-404, CommonMark, HTML5: winners write the spec *after* observing deployment, and the spec codifies practice. Prescriptive-first standards (XHTML2, XSD) select for committee needs over user needs.
7. **Data-model fit with the consumer's native structures.** JSON == dicts/arrays == every language's core types; sexprs' lists and XML's mixed content both forced translation layers. For .sarib the "consumer native structure" is dual: LLM attention over plain text AND programmatic access as records/graphs — the format must map cleanly to both.
8. **Safety defaults.** Post-YAML/billion-laughs, any 2026 format gets security-reviewed on day one: no arbitrary code in load, bounded expansion, canonical form defined early (Rivest had this right in 1997).

## Design lessons for .sarib

1. **Spec size is a survival trait — target "business card," measure in pages.** JSON: six railroad diagrams, frozen. YAML: 86 printed pages, versioned, still evolving — and PEP 518 rejected it *for that stated reason*. Keep the .sarib core grammar small enough that a competent dev writes a conforming parser in a day, and publish the page count as a feature. [Source](https://peps.python.org/pep-0518/) [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell)
2. **Never let syntax guess types; quote/mark everything ambiguous.** The Norway problem, sexagesimal `22:22`, and accidental floats all come from implicit typing of unquoted scalars — "friendliness" that silently corrupts data. TOML's always-quoted strings and JSON's explicit literals are the fix. .sarib semantic fields must be typed by *marker*, never by *lexical shape inference*. [Source](https://hitchdev.com/strictyaml/why/implicit-typing-removed/) [Source](https://toml.io/en/)
3. **Freeze the core; version only extensions.** A document's meaning must never change under a new spec revision (YAML 1.1→1.2 changed what parses as a boolean; JSON never changed and won). Design .sarib so unknown extensions degrade to inert, visible text — the Markdown-inline-HTML / HTML-unknown-tag move — instead of reserving syntax for future reinterpretation. [Source](https://ruudvanasseldonk.com/2023/01/11/the-yaml-document-from-hell) [Source](https://html5forwebdesigners.com/design/)
4. **Ride a carrier that pre-installs the parser, and be backward compatible with it.** Every winner had one (browser/spreadsheet/GitHub); every elegant loser lacked one (sexprs waited 28 years for their RFC). For .sarib the carrier is the LLM+agent stack: if .sarib documents render acceptably as Markdown and parse trivially into JSON-shaped records, both existing "runtimes" adopt it at zero cost — that IS the incremental adoption path. [Source](https://www.rfc-editor.org/rfc/rfc9804.pdf) [Source](https://twobithistory.org/2017/09/21/the-rise-and-rise-of-json.html)
5. **No code execution in load; define the canonical form on day one.** YAML's tag-constructors made `load()` an RCE and its anchors enabled billion-laughs DoS against Kubernetes (CVE-2019-11253); JSON needed 18 years to get canonicalization (RFC 8785) for signing. .sarib should ship: pure-data load semantics, bounded expansion, and a canonical byte form (for hashing/signing/dedup of knowledge units) in v1. [Source](https://github.com/kubernetes/kubernetes/issues/83253) [Source](https://www.rfc-editor.org/rfc/rfc9804.pdf)
6. **Subtract features that threaten interoperability, even beloved ones.** Crockford removing comments (because they were becoming parsing directives) is the single most instructive act in this corpus: the discipline to delete a *useful* feature to protect the ecosystem. For .sarib: any feature whose plausible misuse is "smuggling instructions to specific parsers" (or specific models) should be cut or sandboxed. [Source](https://news.ycombinator.com/item?id=3912149)
7. **Be "discovered, not invented": serialize what already exists in nature.** JSON transcribed JavaScript literals; Markdown transcribed email conventions; CSV transcribed spreadsheet exports. .sarib should transcribe the conventions LLMs and knowledge workers already emit (Markdown prose, key: value front-matter, typed links/tags) rather than introducing novel syntax that must be taught. [Source](https://nofluffjuststuff.com/blog/douglas_crockford/2008/01/the_discovery_of_json) [Source](https://daringfireball.net/projects/markdown/syntax)
8. **Expect to win ugly ("worse is better") — so choose which corners get cut.** Gabriel's mechanism says the simple-implementation format spreads first and gets patched toward the right thing later. Cut completeness (fewer constructs) and cut expressive ceremony — but never cut determinism, safety, or the extension mechanism, because those (per XML, YAML, Markdown respectively) are the cuts that cannot be patched later. [Source](https://www.jwz.org/doc/worse-is-better.html) [Source](https://johnmacfarlane.net/beyond-markdown.html)
