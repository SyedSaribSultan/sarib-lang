# RQ3 — Why did Markdown win despite semantic poverty?

Research notes: adoption physics of markup/document formats (Markdown, org-mode, AsciiDoc, reStructuredText, HTML lineage).
Method: web research, 2026-07-14. Primary sources preferred (Gruber's own pages, Atwood's blog, MacFarlane's essays, contemporaneous accounts). Unverifiable claims are flagged UNVERIFIED.

---

## 1. Markdown — Gruber's original design intent (2004)

- Markdown was created by John Gruber in 2004, with Aaron Swartz as his "sounding board" during design (Gruber later insisted he is the *sole* creator: "I am Markdown's sole creator, not co-creator... Aaron Swartz, whose feedback was instrumental" — tweet, Sept 8, 2014). [Source](https://en.wikipedia.org/wiki/Markdown) [Source](https://onemanandhisblog.com/2014/09/markdown-commonmark-open-source-controversy/)
- The stated design goal, verbatim from the syntax document: "Readability, however, is emphasized above all else. A Markdown-formatted document should be publishable as-is, as plain text, without looking like it's been marked up with tags or formatting instructions." [Source](https://daringfireball.net/projects/markdown/syntax)
- Gruber, verbatim: "the single biggest source of inspiration for Markdown's syntax is the format of plain text email." Punctuation characters were "carefully chosen so as to look like what they mean" (asterisks look like emphasis, `>` looks like email quoting). [Source](https://daringfireball.net/projects/markdown/syntax)
- Markdown deliberately did NOT try to be complete. Gruber: "Markdown is not a replacement for HTML, or even close to it... HTML is a *publishing* format; Markdown is a *writing* format." Anything not covered by the syntax has an escape hatch: "you simply use HTML itself," inline, with no delimiter needed. [Source](https://daringfireball.net/projects/markdown/syntax)
- Markdown's syntax borrowed from prior lightweight formats — Setext, atx (Swartz's own 2002 format), Textile, reStructuredText, Grutatext, EtText — i.e., it was a *synthesis of existing conventions*, not an invention (parallel to Crockford's "JSON was discovered"). [Source](https://daringfireball.net/projects/markdown/syntax)
- Key inversion: Markdown prioritizes the human reader of the *source file*, accepting parsing ambiguity as the cost — the opposite of the usual markup-design priority (machine-unambiguous, human-second). [Source](https://en.wikipedia.org/wiki/Markdown)
- Design tolerated "laziness": lazy list numbering, lazy blockquote continuation, lazy hanging indents are all explicitly permitted in the spec prose. Forgiveness-by-design. [Source](https://daringfireball.net/projects/markdown/syntax)
- Gruber shipped Markdown.pl 1.0 in 2004 and essentially froze it (last release 1.0.1, Dec 2004); he "hasn't seen the need to fiddle with his initial specification... in a decade" (as of 2014). [Source](https://onemanandhisblog.com/2014/09/markdown-commonmark-open-source-controversy/)

## 2. Distribution vs intrinsic merit — how Markdown actually spread

- Stack Overflow (launched 2008) chose Markdown for all questions/answers; Atwood built MarkdownSharp (C#) for it and "learned to refer to Babelmark extensively while working on Stack Overflow and MarkdownSharp." [Source](https://blog.codinghorror.com/standard-flavored-markdown/)
- GitHub (launched 2008) rendered READMEs as Markdown and "had been using its own variant of Markdown since as early as 2009," adding tables, auto-linked issue/commit references, etc. Every repo's front page became a Markdown document — arguably the single largest distribution vehicle. [Source](https://github.blog/engineering/user-experience/a-formal-spec-for-github-markdown/) [Source](https://en.wikipedia.org/wiki/Timeline_of_GitHub)
- Reddit, Discourse, and "dozens of other high-traffic platforms" adopted Markdown dialects for user-generated content; Reddit maintains its own C fork ("snudown"), Discourse mixed Markdown + HTML subset + BBCode. Exact Reddit adoption year: WEAKLY SOURCED (secondary histories only). [Source](https://blog.codinghorror.com/standard-flavored-markdown/) [Source](https://web2md.org/blog/history-of-markdown)
- The adopting platforms were places developers *had to write* (Q&A, code hosting, forums) — Markdown rode distribution, not evangelism. Gruber did essentially no promotion after 2004; the platforms did it for him. (Synthesis from above sources.)
- The 2010s Markdown ecosystem grew bottom-up: static site generators (Jekyll → GitHub Pages), pandoc, editors. Jekyll's Markdown+YAML-front-matter convention became the de facto blog format. WEAKLY SOURCED as a causal claim, but the artifacts are ubiquitous. [Source](https://docs.asciidoctor.org/about/history/)
- By the mid-2020s Markdown became the de facto prompt/output format for LLMs (chat interfaces render it; models emit it), a second unforeseen distribution wave. [Source](https://web2md.org/blog/history-of-markdown) — secondary source; treat the mechanism as observed-but-understudied.

## 3. The CommonMark standardization fight (2009–2014)

- Atwood, 2009 ("Responsible Open Source Code Parenting"): "Right now we have the worst of both worlds. Lack of leadership from the top, and a bunch of fragmented, poorly coordinated community efforts to advance Markdown, none of which are officially canon." [Source](https://blog.codinghorror.com/responsible-open-source-code-parenting/)
- Oct 25, 2012, Atwood, "The Future of Markdown": "I propose that Stack Exchange, GitHub, Meteor, Reddit... work together to come up with an official Markdown specification, and standard test suites... We've all been working at cross purposes for too long, accidentally fragmenting Markdown while popularizing it." [Source](https://blog.codinghorror.com/the-future-of-markdown/)
- The working group (Atwood/Discourse, John MacFarlane/UC Berkeley + pandoc, David Greenspan/Meteor, reps from GitHub, Reddit, Stack Exchange) invited Gruber by email in November 2012 and "never heard back." [Source](https://blog.codinghorror.com/standard-markdown-is-now-common-markdown/)
- The ambiguity evidence: in 2012 *zero* JavaScript Markdown implementations passed MDTest (itself only a community test suite). Atwood's Babelmark demo: a trivial document (heading, paragraph, two lists) produced **15 different rendered outputs across 22 Markdown parsers**. "In Markdown, we literally built a Tower of Babel." [Source](https://blog.codinghorror.com/standard-flavored-markdown/)
- CommonMark's core diagnosis, from commonmark.org: "because nothing in Markdown counts as a 'syntax error,' the divergence often isn't discovered right away." Silent divergence — the format *cannot fail*, so implementations disagree invisibly. [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/)
- Launch and blowup: the spec launched Sept 3, 2014 as "Standard Markdown." Gruber called the name "infuriating," demanded rename, domain shutdown, and an apology; he rejected "any form of the word Markdown" in the name. Renamed "Common Markdown" (Sept 4), then "CommonMark" (Sept 5, 2014). Atwood published a public apology. [Source](https://blog.codinghorror.com/standard-markdown-is-now-common-markdown/) [Source](https://www.infoq.com/news/2014/09/markdown-commonmark)
- Gruber's stated position against standardization (Sept 2014 tweets): "Different sites (and people) have different needs. No one syntax would make all happy." He had also claimed Markdown succeeded *because of*, not despite, the loose spec. [Source](https://www.infoq.com/news/2014/09/markdown-commonmark) [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/)
- Atwood's counter (tweet, Sept 7, 2014): "gruber really honestly believes building on sand (ambiguity built in) is a feature. Earthquakes disagree!" [Source](https://onemanandhisblog.com/2014/09/markdown-commonmark-open-source-controversy/)
- Dave Winer sided with Gruber, framing it as deployment realism: "Programmers always underestimate deployment, and think they can wave a magic wand and get everyone to upgrade." Werner Vogels (Amazon CTO) commented it was "a case of 'Worse is better' — instead of excellent formalized frameworks we favor tools that work." [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/)
- Outcome: CommonMark won de facto without ever getting the name. GitHub rebased GFM on the CommonMark spec in 2017 as "a strict superset of CommonMark" with tables/strikethrough/autolinks/task-lists as formal extensions. The spec-based parsers (cmark, commonmark.js, markdown-it aligned) became the reference implementations everyone embeds. [Source](https://github.blog/engineering/user-experience/a-formal-spec-for-github-markdown/) [Source](https://github.github.com/gfm/)
- Meta-lesson from the fight (Michael Tsai): loose spec helped adoption *early*; the cost appeared only at scale ("How is it more user-friendly to the writer to get different output from different tools?"). Both sides were right at different points on the adoption curve. [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/)

## 4. Markdown's known failure modes (from the spec's own author)

John MacFarlane — the philosopher who wrote the CommonMark spec and both reference implementations — published "Beyond Markdown" (2018) cataloguing what he'd change if not "chained to the past." This is the best available postmortem of Markdown-the-language by its formalizer. [Source](https://johnmacfarlane.net/beyond-markdown.html)

- **Emphasis is formally ambiguous.** `**this* text**` has two consistent readings; the CommonMark spec needs **"17 principles governing emphasis" and "these rules still leave cases undecided."** A `***` mid-word has 8 possible interpretations. Some strings (e.g. `a<em>[b]</em>c`) are *inexpressible* in CommonMark. [Source](https://johnmacfarlane.net/beyond-markdown.html)
- **Reference links break locality.** "We can't tell whether `[foo]` is literal bracketed text or a link... until we've parsed the entire document" — killing syntax highlighting and streaming parsers. [Source](https://johnmacfarlane.net/beyond-markdown.html)
- **Indented code blocks poison list parsing.** "Most of the complexity in the rules for list items is motivated by the need to deal with indented code blocks." [Source](https://johnmacfarlane.net/beyond-markdown.html)
- **Raw HTML pass-through is under-specified and format-locked.** Seven distinct start/end condition pairs for HTML blocks in CommonMark; and as Markdown became a source format for non-HTML outputs, "the way HTML is singled out for raw pass-through has come to seem a bit arbitrary." [Source](https://johnmacfarlane.net/beyond-markdown.html)
- **No attribute/extension mechanism — the semantic ceiling.** "Markdown offers no general way to add attributes (such as classes or identifiers) to elements... It also deprives it of a natural extension mechanism." The only way to attach semantics is dropping to raw HTML. This single missing feature is why every flavor forked instead of extending. [Source](https://johnmacfarlane.net/beyond-markdown.html)
- **Tables were never in the original.** Gruber's answer to tables was inline HTML `<table>` blocks; GFM-style pipe tables are a 2009-era GitHub extension only formally specified in 2017, and remain outside CommonMark core to this day. [Source](https://daringfireball.net/projects/markdown/syntax) [Source](https://github.blog/engineering/user-experience/a-formal-spec-for-github-markdown/)
- **Flavor fragmentation as the price of no extension point:** GFM, MultiMarkdown, PHP Markdown Extra, Pandoc Markdown, R Markdown, Discourse-flavored, snudown... each adds tables/footnotes/attributes incompatibly. The Babelmark result (15 outputs / 22 parsers) is the measurable consequence. [Source](https://blog.codinghorror.com/standard-flavored-markdown/) [Source](https://en.wikipedia.org/wiki/Markdown)
- MacFarlane on the cost of retrofitting rigor: "this respect for the past has made the CommonMark spec a very complicated beast... I despair, at times, of getting to a spec that is worth calling 1.0." Standardizing *after* a decade of loose deployment is vastly harder than specifying up front. [Source](https://johnmacfarlane.net/beyond-markdown.html)

## 5. org-mode — strictly more capable, permanently niche

- Created by Carsten Dominik in 2003 "out of frustration over the user interface of the Emacs Outline mode"; bundled with GNU Emacs by default since Emacs 22 (2006). [Source](https://en.wikipedia.org/wiki/Org-mode) [Source](https://www.gnu.org/software/emacs/manual/html_node/org/History-and-Acknowledgments.html)
- Capability superset of Markdown: outline structure with promote/demote/move operations, TODO states and scheduling metadata attached to headings, agenda views, first-class tables (with a built-in spreadsheet), literate programming via org-babel (executable code blocks, Jupyter-style), export to many formats. [Source](https://news.ycombinator.com/item?id=16198623) [Source](https://news.ycombinator.com/item?id=29265959)
- Why it stayed niche: the format is inseparable from its editor. The features that make org-mode powerful (folding, agenda, babel execution, table recalculation) live in Emacs Lisp, not in the file format; outside Emacs an .org file is just an odd outline. HN consensus framing: org-mode's advantage only materializes for Emacs users. [Source](https://news.ycombinator.com/item?id=16198623)
- Structural point (synthesis, clearly analytic): org-mode had one implementation and one host application; Markdown had hundreds of implementations and no host. A format whose reference experience requires adopting a whole editor inherits that editor's adoption ceiling. Emacs lock-in was org-mode's distribution vehicle *and* its cage.
- Countervailing note: org-mode's single-implementation nature meant it never fragmented the way Markdown did — one tool, one behavior. Consistency via monoculture. (Analytic observation; no single citable source.)

## 6. AsciiDoc — more rigorous, less adopted

- Conceived by Stuart Rackham in 2002 as "a shorthand format for DocBook" (i.e., born with a semantic document model behind it); Rackham maintained AsciiDoc.py 2002–2013. [Source](https://en.wikipedia.org/wiki/AsciiDoc) [Source](https://docs.asciidoctor.org/about/history/)
- Asciidoctor (Ruby reimplementation, 2013) was "motivated by the need to process AsciiDoc in Ruby for use by the GitHub application and for publishing the git documentation online" — i.e., its revival was itself driven by a distribution platform. [Source](https://docs.asciidoctor.org/about/history/)
- Capability: native tables, admonitions, includes, cross-references, footnotes, attributes/roles, multi-output publishing toolchain (HTML5, DocBook, PDF) — the features Markdown lacks — favored in enterprise/technical-docs workflows (O'Reilly's toolchain, the Git book). [Source](https://asciidoctor.org/docs/what-is-asciidoc/) [Source](https://www.adoc-studio.app/blog/why-asciidoc)
- Only began a formal language specification project (at Eclipse Foundation) circa 2020 — nearly two decades after creation; for most of its life "AsciiDoc" meant "whatever AsciiDoc.py/Asciidoctor does." [Source](https://github.com/asciidoctor/asciidoc-docs)
- Why it lost: smaller ecosystem, less Q&A support, and crucially no default rendering on the platforms where developers already were (GitHub renders .adoc but READMEs default to .md; Stack Overflow/Reddit/chat are Markdown-only). Casual contributors "are unlikely to invest even half an hour into learning a new syntax." [Source](https://www.dewanahmed.com/markdown-asciidoc-restructuredtext/) [Source](https://news.ycombinator.com/item?id=33468213)

## 7. reStructuredText — the rigorous one

- First released June 2001 (David Goodger, docutils); adopted as Python's standard docstring/PEP format via PEP 287 (created March 25, 2002). Design goal was an *unambiguous, extensible* lightweight markup — the anti-Markdown on exactly the dimensions Markdown was loose. [Source](https://en.wikipedia.org/wiki/ReStructuredText) [Source](https://peps.python.org/pep-0287/)
- reST has a real extension mechanism: directives (`.. note::`, `.. code-block::`) and roles — semantic extension without forking the grammar. This is the feature MacFarlane wished Markdown had. [Source](https://peps.python.org/pep-0287/) [Source](https://johnmacfarlane.net/beyond-markdown.html)
- Distribution vehicle: Sphinx (first release March 21, 2008) made reST the format of the official Python documentation and, via Read the Docs, of a large slice of the Python ecosystem. [Source](https://en.wikipedia.org/wiki/Sphinx_(documentation_generator))
- Yet it stayed community-bounded: "reStructuredText's steeper learning curve limits adoption outside specialized communities... especially popular in the Python community" — and even Python-adjacent projects have been migrating docs to Markdown (MyST/mkdocs) because casual contributors already know Markdown. [Source](https://www.dewanahmed.com/markdown-asciidoc-restructuredtext/) [Source](https://dasroot.net/posts/2026/03/markdown-vs-asciidoc-vs-restructuredtext-choosing-right-markup-language/)
- Notable: even the PEPs themselves (PEP 287's home turf) moved rendering infrastructure but kept reST; meanwhile Python packaging metadata (pyproject.toml) chose TOML and README rendering on PyPI supports Markdown — the ecosystem that *owned* reST still leaks toward the popular formats. (Analytic observation; see PEP 517/518 discussions.) [Source](https://peps.python.org/pep-0518/)

## 8. HTML lineage note (context for the ceiling argument)

- HTML itself won partly through forgiveness: browsers "produce a reasonable result even in the presence of severe markup errors," per Postel's law — the exact opposite of XML's draconian error handling. Markdown inherited this stance in extreme form: *nothing* is a syntax error. [Source](https://www.w3.org/html/wg/wiki/DraconianErrorHandling) [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/)
- HTML5's design principles — "Support Existing Content," "Pave the Cowpaths," "Evolution, not Revolution" — were codified as a direct reaction to XHTML 2.0's clean-break idealism. Markdown is a pure pave-the-cowpaths artifact: it standardized what email writers already did. [Source](https://html5forwebdesigners.com/design/) [Source](https://daringfireball.net/projects/markdown/syntax)
- The CommonMark/HTML5 rhyme, noted at the time: "HTML5 came from outside the W3C — the Gruber of the analogy — yet it's now adopted by that organization" (Tsai). Standardization succeeded in both cases only when it was *descriptive* (codify deployed behavior) rather than *prescriptive*. [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/)

## 9. The ceiling of plain-text friendliness (synthesis)

- The evidence pattern: every format that beat Markdown on semantics (org-mode, reST, AsciiDoc) lost on distribution; every attempt to make Markdown more semantic either forked it (flavors) or ballooned the spec (CommonMark's 17 emphasis rules). The friendliness that drives adoption and the precision that enables semantics are in direct tension, and Markdown sits at (or defines) the adoption-maximizing point.
- Markdown's ceiling is precisely located: it has containers (emphasis, blockquote, code span/block) but **no attributes and no namespaced extension point** (MacFarlane). Everything beyond ~15 constructs requires either raw-HTML escape or a flavor fork. [Source](https://johnmacfarlane.net/beyond-markdown.html)
- Silent failure is the flip side of forgiveness: "nothing counts as a syntax error" means users never learn the rules and implementations never converge. Formats that want machine semantics need *some* notion of invalidity — but XML shows that total draconian rejection kills casual authorship. The winning zone is: forgiving surface, well-defined parse. [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/) [Source](https://www.tbray.org/ongoing/When/200x/2003/08/19/Draconianism)

## Design lessons for .sarib

1. **Codify existing conventions; don't invent glyphs.** Markdown won by formalizing what people already typed in email; HTML5 won by paving cowpaths; XHTML 2.0 died inventing a cleaner world. For .sarib: every surface construct should look like something humans (and now LLMs) already emit naturally — because LLMs were trained on those same cowpaths. [Source](https://daringfireball.net/projects/markdown/syntax) [Source](https://html5forwebdesigners.com/design/)
2. **Ship the spec and the test suite on day one — retrofitting costs a decade.** Markdown's loose prose spec produced 15 renderings from 22 parsers, and formalizing it afterward produced "a very complicated beast" with 17 emphasis rules that its own author despairs of. .sarib needs a CommonMark-style spec + conformance corpus from v0.1, while keeping Markdown-style tolerance in *what the grammar accepts*. [Source](https://blog.codinghorror.com/standard-flavored-markdown/) [Source](https://johnmacfarlane.net/beyond-markdown.html)
3. **Build the extension mechanism into the core grammar (attributes/namespaces), or suffer flavor fragmentation.** Markdown's single deepest defect is no attribute syntax — so every platform forked (GFM, Extra, MultiMarkdown...). reST's directives show extension-without-forking works. .sarib must have one blessed way to say "here is a construct you don't know; here is how to skip or degrade it." [Source](https://johnmacfarlane.net/beyond-markdown.html) [Source](https://peps.python.org/pep-0287/)
4. **Distribution beats capability; design for a host platform, not against competitors.** org-mode (strictly more capable) stayed inside Emacs; reST stayed inside Python/Sphinx; Markdown rode GitHub/Stack Overflow/Reddit — places people were already forced to write. .sarib's equivalent killer vehicle is agent frameworks/LLM context windows: it must render acceptably wherever Markdown renders today (or *be* valid Markdown at the surface). [Source](https://news.ycombinator.com/item?id=16198623) [Source](https://github.blog/engineering/user-experience/a-formal-spec-for-github-markdown/)
5. **Preserve source-readability as a hard constraint, not a nice-to-have.** Gruber's "publishable as-is, as plain text" rule is the property every winner in this space shares and every loser (XML/DocBook-class) lacks. Semantic richness that destroys plain-text readability moves the format out of the winning category entirely. [Source](https://daringfireball.net/projects/markdown/syntax)
6. **Forgiving surface, deterministic parse — avoid both failure modes.** Markdown's "nothing is a syntax error" caused silent divergence; XML's draconian errors killed casual use. .sarib should parse *every* input deterministically (no fatal errors on prose) but define a strict validity layer on top for the semantic constructs, with lint-grade (not fatal) diagnostics. [Source](https://mjtsai.com/blog/2014/09/10/markdown-and-commonmark/) [Source](https://www.tbray.org/ongoing/When/200x/2003/08/19/Draconianism)
7. **Keep locality: a line's meaning must not depend on the whole document.** MacFarlane's reference-link critique (can't classify `[foo]` until the whole doc is parsed) matters double for .sarib: streaming LLM generation and incremental agent edits both require constructs identifiable "by their shape alone." [Source](https://johnmacfarlane.net/beyond-markdown.html)
8. **Govern the name and the evolution path early.** The 2014 war was fought over a *name* because Gruber had frozen the project but kept the trademark-by-custom; the community had no legitimate upgrade path, so it forked. .sarib should decide at birth: who can extend it, what "conforming" means, and what the name covers — an explicit constitution beats a benevolent-dictator vacuum. [Source](https://blog.codinghorror.com/standard-markdown-is-now-common-markdown/) [Source](https://onemanandhisblog.com/2014/09/markdown-commonmark-open-source-controversy/)
