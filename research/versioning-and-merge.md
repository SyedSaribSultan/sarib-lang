# RQ1 & RQ6 — Identity internals, edit-operation vocabularies, and mergeable formats

Raw research notes for the .sarib language project. Each bullet is a claim with an inline source.
Weakly-sourced or unverified claims are flagged inline as **[WEAK]**, **[INFERENCE]**, or **[UNVERIFIED]**.
Research date: 2026-07-15. Method: web search + primary-source fetches (Pro Git book, RFC 6902, Fowler's event-sourcing article, Yjs INTERNALS.md, Seph Gentle's OT/CRDT postmortem, Shapiro et al. CRDT report, Datomic docs, Mergiraf docs, W3C Turtle). Reuses already-cited identity claims from `semantic-web.md` (Wikidata) and `tools-for-thought.md` (Notion/Roam/org).

The spine of both RQs: **identity-by-content vs identity-by-stable-ID is the core design fork**, and it determines everything downstream — what an "edit operation" can name, and whether two divergent copies can be merged without a human.

## 1. Git — content-addressed identity (the "no stable ID" pole)

Primary source: Pro Git, 2nd ed., "Git Internals — Git Objects." [Source](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

- Git's model is content addressing: "Git is a content-addressable filesystem… at the core of Git is a simple key-value data store." You hand Git content, it returns a key (a hash) that retrieves that content. [Source](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- The key is the SHA-1 (now optionally SHA-256) checksum of the content plus a small header: "This is how Git stores the content initially — as a single file per piece of content, named with the SHA-1 checksum of the content and its header." A blob's identity *is* its content. [Source](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- Git does not store filenames in the object it tracks: "you aren't storing the filename in your system — just the content. This object type is called a blob." The filename lives one level up, as an entry in a *tree* object. [Source](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- Tree objects hold the directory structure: "A single tree object contains one or more entries, each of which is the SHA-1 hash of a blob or subtree with its associated mode, type, and filename." Commits point to a top-level tree plus parent commit(s), author/committer, and message. [Source](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)
- Consequence: **Git tracks content, not files.** Since a blob carries no filename and no stable identity beyond its bytes, Git stores *nothing* that records "file A was renamed to B."
- Renames are therefore recovered **heuristically at diff time**, never tracked. The `git diff`/`git log` machinery uses `-M`/`--find-renames`, pairing a deletion with an addition when their content similarity exceeds a threshold (default 50%), computed with a Rabin-Karp rolling hash; exact-hash matches are paired first. [Source](https://git-scm.com/docs/git-diff) [Source](https://chelseatroy.com/2020/05/09/question-how-does-git-detect-renames/) [Source](https://www.tutorialpedia.org/blog/how-does-git-detect-similar-files-for-its-rename-detection/)
- "Git never stores any information to track renames"; rename detection "occurs during operations like git log or git diff, where Git guesses whether a 'delete + add' is actually a rename by checking content similarity." [Source](https://chelseatroy.com/2020/05/09/question-how-does-git-detect-renames/) **[WEAK — explanatory blogs; the primitive fact (blobs store content only) is from Pro Git above]**
- Git hashes are the canonical example of an ID **humans never type by hand**: even the tutorial concedes "remembering the SHA-1 key for each version of your file isn't practical." Branch/tag refs and porcelain commands exist precisely so authors never touch the 40-char hash. [Source](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

## 2. Human-visible stable IDs in plain text — the tolerance spectrum

The question for .sarib: which ID schemes will humans tolerate *seeing/typing* in a plain-text file, and which must be hidden by tooling?

- **Org-mode `:ID:` / `:CUSTOM_ID:` (org-id.el)** — human-visible stable IDs living in a `:PROPERTIES:` drawer under a headline. `org-id.el` "provides global identifiers for Org-mode entries"; auto-generated `ID`s are "valid across files, which means they need to be absolutely unique" and are tracked globally when `org-id-track-globally` is non-nil (the default). [Source](https://orgmode.org/manual/) [Source](https://git.savannah.gnu.org/cgit/emacs/org-mode.git/tree/lisp/org-id.el)
- `CUSTOM_ID` is author-chosen and readable: stored as `:CUSTOM_ID: my-headline` in the drawer, and "may appear as-is when exported, e.g., as an anchor in HTML." So org exposes *two* tiers: an opaque machine `ID` and a human-readable `CUSTOM_ID`, both in the file but visually quarantined in a drawer. [Source](https://orgmode.org/manual/) **[WEAK — synthesized from manual + org-id.el commentary + community write-ups]**
- **Wikidata Q-IDs — hidden behind labels.** Wikidata uses opaque abstract identifiers (Q42, P31) decoupling name from identifier, but the UI always shows human labels; users edit via forms, never typing Q-numbers into prose (see `semantic-web.md` §7, Vrandečić et al., WWW 2023). [Source](https://iccl.inf.tu-dresden.de/w/images/9/9d/Vrandecic-Pintscher-Kroetzsch_Wikidata-History-WWW-2023.pdf)
- **Notion UUIDs — hidden.** "Everything you see in Notion is a block… every block has an ID (UUIDv4)," but those UUIDs never surface in the editing experience — they live in Postgres and the API, not on the author's screen (see `tools-for-thought.md` §5). [Source](https://www.notion.com/blog/data-model-behind-notion)
- **Roam/Obsidian block IDs — semi-visible.** Roam keys transclusion on per-block UIDs (`((uid))`), and Obsidian on caret markers (`^block-id`) appended in the source; these are tooling-inserted and only partly human-facing — visible in the file but rarely typed from scratch. Roam block references are read-only ("you cannot change the content of a block reference"); block embeds are editable. [Source](https://github.com/Kinneyzhang/roam-block) **[WEAK — Roam's own reference docs are app-internal; described via an Emacs reimplementation + community docs]**
- Pattern across all five: **the more opaque the ID, the more completely tooling must hide it.** Human-readable slugs (`CUSTOM_ID`, wiki-titles) can sit in the text; UUIDs/hashes/Q-numbers must be generated and resolved by the system, surfaced only as labels or links.

## 3. CRDTs — the foundational split (Shapiro et al.)

Primary source: Shapiro, Preguiça, Baquero, Zawirski, "A comprehensive study of Convergent and Commutative Replicated Data Types," INRIA RR-7506 / "Conflict-free Replicated Data Types," SSS 2011. [Source](https://inria.hal.science/inria-00609399) [Source](https://reed.cs.depaul.edu/lperkovic/csc536/lecture10/techreport.pdf)

- A CRDT is a replicated data type engineered so that concurrent updates can be merged automatically with no coordination and no conflict, guaranteeing **Strong Eventual Consistency (SEC)**: any two replicas that have received the same set of updates are in the same state. [Source](https://reed.cs.depaul.edu/lperkovic/csc536/lecture10/techreport.pdf)
- Two dual formulations:
  - **State-based / CvRDT ("convergent")** — replicas transmit their whole state; a merge function computes the *least upper bound*. Convergence follows if states form a monotonic join-semilattice (updates are inflationary and merge is commutative/associative/idempotent). [Source](https://reed.cs.depaul.edu/lperkovic/csc536/lecture10/techreport.pdf) [Source](https://webarchive.di.uminho.pt/haslab.uminho.pt/cbm/publications/comprehensive-study-convergent-and-commutative-replicated-data-types.html)
  - **Operation-based / CmRDT ("commutative")** — replicas broadcast the operations themselves; convergence follows if all *concurrent* operations commute, so any delivery order yields the same result. [Source](https://reed.cs.depaul.edu/lperkovic/csc536/lecture10/techreport.pdf)
- This is the theoretical license for .sarib's "ops as canonical, state as projection" stance: if the op vocabulary is designed so concurrent ops commute (or state forms a semilattice), replicas of a document converge with no central arbiter.

## 4. Automerge — operation-based JSON CRDT (change/patch model + RGA)

Primary sources: automerge.org docs & repo (Martin Kleppmann et al.). [Source](https://automerge.org/docs/) [Source](https://github.com/automerge/automerge)

- Automerge is "a JSON-like data structure (a CRDT) that can be modified concurrently by different users, and merged again automatically without requiring any central server," authored by Martin Kleppmann. [Source](https://github.com/automerge/automerge)
- Internal representation is a monotonically growing **OpSet**: a set of operations exchanged between peers and merged by taking their union; operations are never removed, and each operation "sets or deletes the value on a single key or a single element in a list." State is a *fold* over this op-set. [Source](https://liangrunda.com/posts/automerge-internal-1/) **[WEAK — explanatory internals write-up; corroborated by Yjs INTERNALS §5 below]**
- Every operation is assigned a unique **opID** implemented as a **Lamport timestamp** (a `(counter, actorID)` pair); each replica has a random **actorID**. Deterministic tie-breaking on `(counter, actorID)` guarantees all replicas converge to the same value. [Source](https://liangrunda.com/posts/automerge-internal-1/) [Source](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md)
- The list/text datatype is **RGA-style** (Replicated Growable Array): "the underlying data structure is an RGA sequence… concurrent insertions and deletions can be merged in a manner which attempts to preserve user intent." Deleted elements become tombstones rather than being erased. [Source](https://github.com/automerge/automerge)
- The API surface is **changes** (batches of ops produced by a local edit) and **patches** (the diff applied to materialized state on receipt) — i.e., the document is authored as state but transmitted and stored as operations. [Source](https://automerge.org/docs/)

## 5. Yjs — YATA algorithm (clientID + clock identity)

Primary source: `yjs/INTERNALS.md` (Kevin Jahns). [Source](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md) — algorithm from the YATA paper (2016). [Source](https://www.researchgate.net/publication/310212186_Near_Real-Time_Peer-to-Peer_Shared_Editing_on_Extensible_Data_Types)

- "At its heart, Yjs is a list CRDT" — arrays, text, and maps are all "squeezed into a list in order to reuse the CRDT resolution algorithm." [Source](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md)
- Identity: "Each client is assigned a unique *clientID*… a random 53-bit integer." "Everything inserted in a Yjs document is given a unique ID, formed from a *ID(clientID, clock)* pair (also known as a Lamport Timestamp). The clock counts up from 0 with the first inserted character or item a client makes." Explicitly "similar to automerge's operation IDs." [Source](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md)
- Concurrent-insert ordering (the core of YATA): each item stores the IDs of its left/right neighbours at insertion time (`origin` and `originRight`); the `integrate()` method uses these plus clientID priority to make "list items always resolve to the same order on all peers." [Source](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md)
- Insert vs delete are handled asymmetrically: "Insertions are implemented as a sequential operation based CRDT, but deletions are treated as a simpler state based CRDT." Deleted items are flagged (tombstoned) and optionally garbage-collected; no per-deletion metadata (who/when) is kept. [Source](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md)
- Sync uses a **state vector** — "the known state of each user (a set of tuples (client, clock))" — so a peer can request exactly the operations it is missing. [Source](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md)

## 6. OT vs CRDT — why Google Docs kept OT but new systems chose CRDTs

Primary source: Seph Gentle (Joseph Gentle), "I was wrong. CRDTs are the future" (2020). Gentle worked on **Google Wave**'s OT engine and reimplemented it as **ShareJS** — a rare insider postmortem. [Source](https://josephg.com/blog/crdts-are-the-future/)

- OT records a chronological operation log per document ("Type an *H* at position 0"…) and, on concurrent edits, *transforms* incoming ops against the log to fix up character positions — "It's like realtime git-rebase." The Wave algorithm derived from the 1995 Jupiter paper. [Source](https://josephg.com/blog/crdts-are-the-future/)
- The decisive limitation: **"The big problem with OT is that dependancy on a centralized server."** "You need a centralized server to globally order operations." This is why Google Docs pins each open document to one server and shows the "This document is overloaded so editing is disabled" message under viral load. [Source](https://josephg.com/blog/crdts-are-the-future/)
- Federation/offline (Wave's goal of replacing email) fought OT the whole way: the tree-of-servers scheme "never really worked… Its all just too complicated." [Source](https://josephg.com/blog/crdts-are-the-future/)
- CRDTs "approach the problem slightly differently to allow realtime editing without needing a central source of truth" — the property new peer-to-peer / local-first systems want; modern implementations are "Automerge / RGA or y.js / YATA." [Source](https://josephg.com/blog/crdts-are-the-future/)
- The CRDT cost is **metadata weight**: "Because of how CRDTs work, documents grow without bound," tombstones and per-element IDs accumulate (his example: 83MB to represent a 100KB document in an early Automerge; Yjs' columnar encoding later cut this to ~1.5–2× the text size). [Source](https://josephg.com/blog/crdts-are-the-future/)
- The framing that maps directly onto .sarib's file-ownership thesis: with `git push` "I'm only *notifying* github about the change… My repository is mine," whereas editing a Google Doc means "asking Google for *permission* to edit the file." OT belongs to centralized software; CRDTs belong to owned, local files. [Source](https://josephg.com/blog/crdts-are-the-future/)
- Historical footnote (why Google *still* runs OT): Google Docs was built in 2006, before CRDT theory matured, and had already invested heavily in the Jupiter-model OT by the time CRDTs were production-ready. [Source](https://systemdr.systemdrd.com/p/crdts-vs-operational-transformation) **[WEAK — secondary summary]**

## 7. Datomic — immutable facts, assertion/retraction, database-as-a-value

Primary source: Datomic documentation (glossary, transaction model, indexes). [Source](https://docs.datomic.com/glossary.html) [Source](https://docs.datomic.com/transactions/model.html) [Source](https://docs.datomic.com/indexes/index-model.html)

- The atom of storage is a **datom**: "an immutable, point-in-time fact: [entity, attribute, value, transaction, added]." [Source](https://docs.datomic.com/glossary.html)
- The schema echoes RDF but adds time and an added/retracted bit: "Each datom associates an entity (E) with a value (V) via an attribute (A), similar to the subject/predicate/object of RDF," with the transaction (T) recording *when*. The base index sorts E→A→V→T (**EAVT**). [Source](https://docs.datomic.com/glossary.html) [Source](https://docs.datomic.com/indexes/index-model.html)
- Deletion is not destructive: "There are two kinds of datoms, additions and retractions, named via `:db/add` and `:db/retract`… An addition indicates that a fact is true at a point in time, and a retraction indicates that a fact is *not* true at a point in time." Retracting a fact adds a new datom; the old one is never overwritten. [Source](https://docs.datomic.com/transactions/model.html)
- **Database as a value / accretion-only**: "Datomic is a functional database: databases are immutable values"; `d/transact` is built on the pure function `d/with`, which "takes a database value and a set of information (held to be true at a point in time), and returns a new database value that includes, *via accretion*, that new information." History is never mutated, only extended. [Source](https://docs.datomic.com/transactions/model.html)
- This is the closest existing production system to .sarib's intended stance: **facts (ops) are the canonical, append-only truth; any current "state" is a query over the accreted datoms as of a transaction point** (Datomic's "database as a value" = state-as-projection over an event log).

## 8. Event sourcing — ops are the source of truth, state is a fold

Primary source: Martin Fowler, "Event Sourcing" (2005). [Source](https://martinfowler.com/eaaDev/EventSourcing.html)

- Definition: "Capture all changes to an application state as a sequence of events." "The fundamental idea… is that of ensuring every change to the state of an application is captured in an event object, and that these event objects are themselves stored in the sequence they were applied for the same lifetime as the application state itself." [Source](https://martinfowler.com/eaaDev/EventSourcing.html)
- Current state is explicitly a **projection** you can throw away and recompute — "Complete Rebuild: We can discard the application state completely and rebuild it by re-running the events from the event log on an empty application" — plus "Temporal Query" (state as of any past point) and "Event Replay." This is precisely .sarib's "ops canonical, state as projection." [Source](https://martinfowler.com/eaaDev/EventSourcing.html)
- Fowler's own canonical example: **"A common example of an application that uses Event Sourcing is a version control system."** [Source](https://martinfowler.com/eaaDev/EventSourcing.html)
- Design guidance directly relevant to op vocabulary: **difference-form events are reversible, absolute ones are not** — "'add $10 to Martin's account' as opposed to 'set Martin's account to $110'… in the former case I can reverse by just subtracting $10, but in the latter case I don't have enough information to recreate the past value." Prefer relative/commutative ops. [Source](https://martinfowler.com/eaaDev/EventSourcing.html)
- Scaling upside of an op-log canonical form: "the event log is a purely additive structure that requires minimal locking" — append-only logs are cheap to replicate (the same reason Datomic and CRDTs accrete). [Source](https://martinfowler.com/eaaDev/EventSourcing.html)

## 9. JSON Patch (RFC 6902) — a concrete op vocabulary and its failure modes

Primary source: RFC 6902, "JavaScript Object Notation (JSON) Patch" (Bryan & Nottingham, IETF, 2013). [Source](https://www.rfc-editor.org/rfc/rfc6902)

- JSON Patch "defines a JSON document structure for expressing a sequence of operations to apply to a… JSON document." A patch is an ordered array of operation objects. [Source](https://www.rfc-editor.org/rfc/rfc6902)
- The op vocabulary is six verbs: **add, remove, replace, move, copy, test.** Each op names an `op` and a `path` (a JSON Pointer, RFC 6901); `move`/`copy` add a `from`; `add`/`replace`/`test` add a `value`. [Source](https://www.rfc-editor.org/rfc/rfc6902) [Source](https://www.rfc-editor.org/rfc/rfc6901)
- Ops are strictly sequential and all-or-nothing: "Operations are applied sequentially in the order they appear in the array… the resulting document becomes the target of the next operation," and on any failure "application of the entire patch document SHALL NOT be deemed successful" (the PATCH is atomic). [Source](https://www.rfc-editor.org/rfc/rfc6902)
- `test` is a **precondition** op (optimistic concurrency guard), not a merge primitive: it "tests that a value at the target location is equal to a specified value" and aborts the patch otherwise. [Source](https://www.rfc-editor.org/rfc/rfc6902)
- **The array-index fragility**: arrays are addressed purely by position. `add` to an array means "Any elements at or above the specified index are shifted one position to the right"; `remove` shifts "any elements above the specified index… one position to the left." A patch that says `{"op":"add","path":"/foo/1",…}` refers to *whatever is at index 1 now*, not to a specific element. [Source](https://www.rfc-editor.org/rfc/rfc6902)
- **No element identity → concurrent-edit hazard**: because there is no per-element ID (only positions), two patches generated independently against the same array cannot be safely combined — an insert in one shifts every later index the other assumed. JSON Patch is a transport for *one* diff against a *known* base version, not a merge format. [Source](https://www.rfc-editor.org/rfc/rfc6902) **[INFERENCE — the positional shifting behavior is normative in the RFC; the "unsafe under concurrency" conclusion is the standard reading and is exactly the gap CRDT element-IDs (§4–5) fill]**
- Lesson for .sarib's op design: JSON Patch is the anti-pattern to CRDTs on the one axis that matters — it addresses list positions, not identified elements — which is why it cannot merge, while Automerge/Yjs can.

## 10. Structured / semantic merge — why line-based 3-way fails on structured data

Primary sources: Mergiraf docs + LWN coverage; difftastic. [Source](https://mergiraf.org/architecture.html) [Source](https://lwn.net/Articles/1042355/) [Source](https://github.com/Wilfred/difftastic)

- Git's default merge (`git merge`, built on diff3) is **line-oriented and language-agnostic**. That makes it fast and universal but blind to structure: it "report[s] many spurious conflicts (false positives) and miss[es] real conflicts (false negatives)." [Source](https://lwn.net/Articles/1042355/) [Source](https://mergiraf.org/architecture.html)
- The same line-based blindness is what broke Jupyter notebooks under git: "primitive line-based diff and merge tools do not handle well the logical structure of notebook documents" (see `tools-for-thought.md` §4). [Source](https://jupyter.org/enhancement-proposals/08-notebook-diff/notebook-diff.html)
- **Mergiraf** does structured merge: it parses each side with **tree-sitter** into a generic syntax tree ("each leaf corresponds to a specific token… each internal node represents a language construct"), then merges on the trees, which "reduce[s] false positives and detect[s] more real conflicts." It runs a cheap line-based merge first and only falls back to tree merge where that fails. Already supports 33 languages. [Source](https://mergiraf.org/architecture.html) [Source](https://lwn.net/Articles/1042355/)
- **difftastic** is the diff-side analogue: "a structural diff that understands syntax," diffing ASTs rather than lines. [Source](https://github.com/Wilfred/difftastic)
- What makes a format mergeable (synthesis of §§3–10): (1) **explicit, addressable structure** (nodes/elements a merge can align), (2) **stable identity per element** (so alignment survives moves/renames, unlike positional JSON Patch or line numbers), and (3) **an operation model whose concurrent ops commute** (CRDT-style) or at least a semantic unit the merge can reason about (AST nodes). Line-of-text is none of these; a labeled-property-graph of identified nodes is all three. **[INFERENCE — synthesis across the cited sources]**

## Design lessons for .sarib

1. **Assign durable node/edge IDs; do not rely on content identity.** Git is the cautionary tale: because a blob is only content and the filename lives elsewhere, Git *cannot* track a rename and must re-guess it heuristically at diff time (`-M`, 50% similarity). A knowledge medium whose whole point is stable relationships must give every node an identity that survives renaming, moving, and rewording — identity-by-stable-ID, not identity-by-content. [Pro Git](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects), [git-diff](https://git-scm.com/docs/git-diff)

2. **Make operations the canonical, append-only truth and treat current state as a projection.** Event sourcing, Datomic's "database as a value" (accretion-only), and both CRDT families independently converge on this. Fowler even names a VCS as the archetype. For .sarib this means the op-log is authoritative and any rendered document/graph is a fold over it that can be discarded and rebuilt (Complete Rebuild / Temporal Query come for free). [Fowler](https://martinfowler.com/eaaDev/EventSourcing.html), [Datomic](https://docs.datomic.com/transactions/model.html)

3. **Retract, never destroy.** Datomic models deletion as a *new fact* (`:db/retract` = "not true at a point in time"), keeping history intact and auditable; Yjs and Automerge keep tombstones for the same convergence reason. This also lines up with `semantic-web.md`'s "record claims, not truth" (Wikidata plurality). Deletion in .sarib should be an assertion about a node's status, not an erasure of it. [Datomic](https://docs.datomic.com/transactions/model.html), [Yjs INTERNALS](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md)

4. **Give every element a globally-unique `(replica, counter)` ID; forbid positional addressing in the op vocabulary.** The entire difference between mergeable and unmergeable is here: Automerge's opIDs and Yjs' `ID(clientID, clock)` Lamport pairs let concurrent edits merge with no server, whereas JSON Patch's array-index paths and OT's character offsets break the moment a concurrent insert shifts positions. .sarib ops must reference identified elements, and should prefer difference-form/commutative operations (Fowler's "+$10" over "=$110"). [Yjs INTERNALS](https://raw.githubusercontent.com/yjs/yjs/main/INTERNALS.md), [RFC 6902](https://www.rfc-editor.org/rfc/rfc6902), [Fowler](https://martinfowler.com/eaaDev/EventSourcing.html)

5. **Choose CRDT-style merge over OT because .sarib files are owned, local, and offline-first — but budget for metadata weight.** Gentle's Wave/ShareJS postmortem is decisive: OT needs a central server to order operations (the reason Google Docs pins a doc to one machine), while CRDTs merge peer-to-peer — the `git push` "notify, don't ask permission" model .sarib wants. The price is per-element IDs and tombstones that make documents grow, so a columnar/compact encoding (à la Yjs) is not optional at scale. [Seph Gentle](https://josephg.com/blog/crdts-are-the-future/)

6. **Be mergeable at the node/edge level, not the line level.** Line-based 3-way merge (diff3/`git merge`) generates false conflicts and misses real ones on any structured data — the documented cause of the notebook-in-git disaster; Mergiraf/difftastic fix it by operating on syntax trees. Because .sarib is a labeled-property-graph of identified nodes, it can define its *own* semantic merge (align by node ID, merge properties/edges) and never fall back to hoping line diffs line up. [Mergiraf](https://mergiraf.org/architecture.html), [Jupyter JEP](https://jupyter.org/enhancement-proposals/08-notebook-diff/notebook-diff.html)

7. **Hide opaque IDs; let humans read and type only names/slugs.** Across Wikidata (Q-IDs), Notion (UUIDs), Git (SHA hashes — "not practical" to remember), block-ref tools, and org-mode, the rule holds: the more opaque the identifier, the more completely tooling must keep it off the author's screen. .sarib should auto-assign durable machine IDs, resolve links by human-readable name, and — if any ID must appear in the text — make it a readable `CUSTOM_ID`-style slug quarantined from prose. [Wikidata (WWW 2023)](https://iccl.inf.tu-dresden.de/w/images/9/9d/Vrandecic-Pintscher-Kroetzsch_Wikidata-History-WWW-2023.pdf), [Notion](https://www.notion.com/blog/data-model-behind-notion), [org-id.el](https://git.savannah.gnu.org/cgit/emacs/org-mode.git/tree/lisp/org-id.el)

8. **Design the op set so concurrent ops commute (or state forms a semilattice) — that is the actual precondition for automatic merge.** Shapiro et al.'s CmRDT/CvRDT result is the formal license behind lessons 2–6: SEC (no-conflict convergence) is achievable *only* if the operation model was built for it. .sarib's edit-operation vocabulary should be specified against this property from day one, not retrofitted. [Shapiro et al.](https://reed.cs.depaul.edu/lperkovic/csc536/lecture10/techreport.pdf)
