# RQ5 — Single-Source-Many-Views Systems: Where Round-Tripping Breaks

Research notes for the .sarib project ("store knowledge once, render it infinitely").
Beat: every prior system that promised one canonical source with many renderings, and precisely where the round trip failed or held.

Per-system extraction grid: (a) what is canonical, (b) which direction edits flow, (c) where identity is lost in projection, (d) why round-trip broke or held.

Confidence labels: claims are cited inline. Anything marked **[WEAK]** rests on a secondary blog or single source; anything marked **UNVERIFIED** could not be confirmed against a source and should not be repeated without checking.

---

## 1. XML + XSLT — the original "one source, many renderings" dream

**(a) Canonical:** the XML document instance (optionally schema-validated). **(b) Edit flow:** strictly one-way, source → stylesheet → output; there is no defined back channel. **(c) Identity loss:** XSLT output (HTML, PDF via FO) carries no machine link back to source nodes unless the stylesheet author deliberately emits one; the transform is an arbitrary function, so node identity is discarded by construction. **(d) Verdict:** round-trip was never attempted — the model held as a pure one-way pipeline in industrial publishing and died as a general-purpose paradigm.

- Around 2000 the vision was that "nearly all programming would be a matter of transporting and transforming XML... XML would be the universal data format," and XSLT was the language designed for that world; it "never became extremely popular," blamed on awkward angle-bracket syntax and the declarative/functional style being uncomfortable for most developers. [Source](https://www.johndcook.com/blog/2009/03/16/what-happened-to-xslt/)
- Practitioner comments on the same post pin the failure on the split between XSLT 1.0 ("lacks so many features that it makes you cry") and the lack of browser/runtime support for XSLT 2.0 — the standard improved but the deployed platform froze at 1.0. [Source](https://www.johndcook.com/blog/2009/03/16/what-happened-to-xslt/)
- The browser story is now formally over: Chrome is deprecating and removing XSLT (XSLTProcessor and the XSL processing instruction), disabling it for stable users in Chrome 158 (Nov 2026), citing the unmaintained libxslt C codebase and memory-safety risk; Firefox and WebKit have signaled the same intent. [Source](https://developer.chrome.com/docs/web-platform/deprecating-xslt) [Source](https://groups.google.com/a/chromium.org/g/blink-dev/c/CxL4gYZeSJA)
- Where the XML pipeline *survives*: structured technical documentation. DITA is "a structured, XML-based way to write content as small, reusable topics and publish it to many output formats" — write once, reuse, publish to multiple deliverables. [Source](https://technicalwriterhq.com/writing/technical-writing/darwin-information-typing-architecture-dita/)
- The DITA Open Toolkit — the reference publishing engine — is literally an Ant + XSLT + Java pipeline; all default output formats are plugins over XSLT modules. XSLT didn't die; it retreated into server-side publishing where the one-way assumption is honest. [Source](https://www.dita-ot.org/dev/reference/architecture.html)
- DocBook remains the "document-oriented" counterpart to DITA's topic/reuse orientation; both persist in large documentation programs. [Source](https://paligo.net/blog/technical-writing/docbook-vs-dita/) In aerospace/defense, the S1000D XML spec (20+ years old) is still the standard for technical publications. [Source](https://www.stilo.com/dita-xml-faqs/is-dita-compliant-with-industry-standards-like-docbook-or-s1000d/)
- Interpretation for .sarib: single-source-many-outputs *works* when (1) authors only ever touch the source, (2) a professional toolchain owns the render, and (3) the economic payoff (regulatory reuse, translation) justifies the authoring pain. It failed as a mass paradigm because the source format was hostile to humans and the projections were terminal (nothing flows back).

## 2. Org-mode — outline → export, deliberately one-directional (with one revealing exception)

**(a) Canonical:** the plain-text `.org` file in Emacs. **(b) Edit flow:** one-way for documents (org → HTML/LaTeX/ODT/…); *two-way for source-code blocks only*, via tangle/detangle. **(c) Identity loss:** prose exports drop all provenance — an exported HTML paragraph has no stable link back to its org heading; tangled code keeps identity only if you opt into comment-link anchors. **(d) Verdict:** document round-trip never existed by design; the code round-trip (detangle) works precisely because the projection embeds back-links, and it is fragile.

- The Org manual frames export as one-way conversion: "Org can convert and export documents to a variety of other formats while retaining as much structure... and markup as possible," via backends (ascii, beamer, html, icalendar, latex, md, odt, org, texinfo, man). Nothing in the export architecture ingests edits from outputs. [Source](https://orgmode.org/manual/Exporting.html)
- Note the manual's own hedge — "as much structure as possible" — an admission that projection is lossy even outbound.
- Org-babel supports `org-babel-tangle` (extract code blocks to source files) and, in the reverse direction, `org-babel-detangle`, which propagates edits made in the tangled source file back into the org file. [Source](https://orgmode.org/manual/Extracting-Source-Code.html)
- Detangle only works if the code was tangled with `:comments yes` (or `link`) so that Org inserts link comments into the generated source — i.e., the projection must carry explicit identity anchors for the back-flow to find its target. [Source](https://orgmode.org/manual/Extracting-Source-Code.html) The feature was introduced as "detangle changes in code files back to the original org files." [Source](https://code.orgmode.org/bzg/org-mode/commit/2152f1ec28dab77a3b8ee86ca012d19b1351882e)
- The mechanism is acknowledged as brittle: mailing-list bug reports show detangle breaking when block contents collide with the link syntax used as anchors (e.g., literal `[[...]]` in code bodies). Identity carried in-band as comments is fragile identity. [Source](https://list.orgmode.org/orgmode/87jysrbejg.fsf@bhw-yoga.localdomain/)
- Interpretation: org-mode is a natural experiment. Same tool, two projections: HTML export (no identity → no back-flow, nobody even asks for it) vs tangled code with comment anchors (identity → working but fragile round-trip). The round-trip boundary tracks exactly where identity survives projection.

## 3. Literate programming — Knuth's WEB: tangle/weave as two projections of one source

**(a) Canonical:** the `.web` file — prose + code chunks in psychological order. **(b) Edit flow:** one-way only: WEB → TANGLE → compilable Pascal; WEB → WEAVE → TeX documentation. Humans never edit tangled output. **(c) Identity loss:** total and *intentional* — TANGLE "scrambles" chunks into compiler order, producing deliberately unreadable code; the woven TeX is print-only. **(d) Verdict:** consistency held by construction because exactly one representation accepted human edits; adoption failed anyway.

- Knuth introduced literate programming in 1984; tools "obtain two representations from a source file: one understandable by a compiler..., the 'tangled' code, and another for viewing as formatted documentation, ... 'woven' from the literate source." "Weaving and tangling are done on the same source so that they are consistent with each other." [Source](https://en.wikipedia.org/wiki/Literate_programming)
- Original paper: Knuth, "Literate Programming," The Computer Journal 27(2), 1984 — the canonical statement of programs as literature and of the WEB/TANGLE/WEAVE design. [Source](http://www.literateprogramming.com/knuthweb.pdf)
- Knuth on why one source: "a program is best thought of as a web instead of a tree... in whatever order is best for human comprehension"; "TANGLE is able to scramble everything up into the arrangement that a PASCAL compiler demands." The compiler-facing projection was explicitly write-only. [Source](https://en.wikipedia.org/wiki/Literate_programming)
- Knuth (2008): "literate programming is certainly the most important thing that came out of the TeX project... it has actually been indispensable at times," e.g., the MMIX meta-simulator. Proof at scale exists — TeX and METAFONT are published literate programs. [Source](https://www.informit.com/articles/article.aspx?p=1193856)
- Why it never went mainstream despite Knuth's stature: (1) it demands that programmers also be good prose writers and storytellers — "if this is done poorly, the result is harder to understand than traditional programs" [Source](https://johtela.github.io/LiterateCS/Introduction.html); (2) the concept was diluted — doc generators (Javadoc, POD) got called "literate" while lacking the web of reorderable macros, the actual point (Dominus, "POD is not Literate Programming") [Source](https://www.perl.com/pub/tchrist/litprog.html/); (3) tooling friction: every language needed a WEB dialect, and debuggers/compilers pointed at tangled output, not the source you wrote — the projection you debugged in was not the projection you edited. **[WEAK — the debugger-mismatch point is standard lore; Nørmark's "Literate Programming — Issues and Problems" discusses tool-chain friction]** [Source](https://www.cs.aau.dk/~normark/litpro/issues-and-problems.html)
- Wikipedia's tool survey classifies notebooks (Jupyter etc.) as "semi-literate": cellular execution but no macros/reordering — the 2010s resurgence kept the prose-plus-code surface and dropped the many-projections core. [Source](https://en.wikipedia.org/wiki/Literate_programming)
- Interpretation: WEB is the cleanest existence proof that N projections from one source stay consistent iff N−1 of them are read-only. It is also the cleanest proof that technical correctness of the projection model does not buy adoption if authoring cost is high and the ecosystem (debuggers, compilers, colleagues) lives in a projection.

## 4. Jupyter notebooks + jupytext — two representations that both accept edits

**(a) Canonical:** the `.ipynb` JSON file — inputs, outputs, execution counts, kernel/environment metadata in one blob. With jupytext pairing, canonicality is *split*: text file owns inputs, ipynb owns outputs. **(b) Edit flow:** normally editor ↔ ipynb; with jupytext, edits flow text→notebook on reload and notebook→text on save, reconciled by file timestamps. **(c) Identity loss:** cells have no stable IDs in the text representation — sync matches by position/content; outputs are simply absent from the text projection. **(d) Verdict:** raw ipynb+git broke spectacularly; jupytext round-trips by partitioning ownership, and its failure modes appear exactly when both representations are edited between syncs.

- The core git pain, from Jupyter's own enhancement proposal: "primitive line-based diff and merge tools do not handle well the logical structure of notebook documents." [Source](https://jupyter.org/enhancement-proposals/08-notebook-diff/notebook-diff.html)
- fast.ai (Jeremy Howard) diagnosis: git conflict markers inserted into JSON produce a file that "is not valid JSON, and therefore Jupyter can't open it"; every cell stores an execution count, so "if you and a colleague run the cells in different orders, you'll have a conflict in every single cell"; matplotlib reprs embed memory addresses that change every run; kernel metadata differs across machines so two people saving an *unchanged* notebook can conflict. [Source](https://www.fast.ai/posts/2022-08-25-jupyter-git.html)
- Workaround #1, nbdime: content-aware diffing/merging that guarantees a conflicted notebook is still a valid, openable notebook. [Source](https://nbdime.readthedocs.io/)
- Workaround #2, nbdev2: a git merge driver that re-merges at cell level using only cell *source* (ignoring outputs/metadata, via `difflib.SequenceMatcher` with `__eq__`/`__hash__` defined on source only), plus a Jupyter save hook that strips execution counts and unneeded metadata before they ever hit git. Howard: "The Jupyter+git problem has been totally solved." [Source](https://www.fast.ai/posts/2022-08-25-jupyter-git.html)
- Workaround #3, jupytext — the real round-trip system. Its own docs: text notebooks contain "only the notebook inputs (and optionally, the metadata)"; "the notebook outputs are lost when the notebook is closed, as only the notebook inputs are saved in text notebooks." [Source](https://github.com/mwouts/jupytext)
- Jupytext's sync model for paired notebooks: "You can edit the .py version... and get the edits back in Jupyter by selecting reload notebook from disk. The outputs will be reloaded from the .ipynb file"; `jupytext --sync` loads "the inputs from the most recent paired file." Ownership is partitioned: text owns inputs, ipynb owns outputs, recency decides. [Source](https://github.com/mwouts/jupytext)
- Jupytext's documented failure mode is concurrent edits: "If Jupyter tries to save the notebook while the paired .py file has also been edited on disk since the last reload, a conflict will be detected and you will be asked to decide which version of the notebook (in memory or on disk) is the appropriate one." Two edit-accepting representations → human arbitration. [Source](https://github.com/mwouts/jupytext)
- fast.ai's critique of jupytext confirms the boundary: if you want to keep outputs, "managing this linkage gets complex, and ends up with the Jupyter+git problem all over again!" [Source](https://www.fast.ai/posts/2022-08-25-jupyter-git.html)
- Interpretation: the notebook mess is a *conflation* failure — one file format storing three different kinds of state (human-authored inputs, machine-generated outputs, environment metadata) with different ownership and volatility. Every successful fix (nbdev save hook, jupytext pairing) works by separating state classes and assigning each a single owner.

## 5. Notion — blocks database with views; the closest living realization

**(a) Canonical:** the block graph in Notion's Postgres — every block a record with UUID, type, properties, content array (render tree), parent pointer (permissions). There is *no plain-text canonical form*. **(b) Edit flow:** all edits go through the app/API to the block store; views are live windows onto it, so edits in any view mutate the same records. Export is one-way and terminal. **(c) Identity loss:** none internally (block IDs are stable, and even hidden properties survive type changes); total at the export boundary (IDs, views, relations, formulas dropped). **(d) Verdict:** round-trip *inside* the walled garden holds via universal block identity; round-trip *across* the boundary is officially impossible.

- Official data model (Jake Teton-Landis, 2021): "Everything you see in Notion is a block. Text, images, lists, a row in a database, even pages themselves"; every block has an ID (UUIDv4), properties, a type, a content array of child block IDs, and a parent pointer used only for permissions. [Source](https://www.notion.com/blog/data-model-behind-notion)
- Identity survives projection-change: "Changing the type of a block doesn't change the block's properties or content — it only changes the type attribute. The information is just rendered differently, or even ignored" — a checked to-do turned into a Heading, then a Callout, then back into a to-do is *still checked*. Notion states the design goal outright: "we preserve as much user intention as possible." This is the strongest living example of a view transform that never drops hidden state. [Source](https://www.notion.com/blog/data-model-behind-notion)
- Indentation is structural, not presentational: "when you indent something in Notion, you are manipulating relationships between blocks and their content, not just adding a style." The render tree *is* the data. [Source](https://www.notion.com/blog/data-model-behind-notion)
- Views are saved configurations (filter/sort/group/layout) over one data source, not derived documents — table/board/timeline/calendar/list/gallery/chart/form are all layouts of the same rows. [Source](https://www.notion.com/help/views-filters-and-sorts)
- Export is lossy and Notion says so operationally: databases export as CSV; "you can only choose between the current view and the default view. Exporting all views at once isn't supported"; Form views can't be exported at all; callouts export as HTML because Markdown has no equivalent; and — the decisive line — "You can't instantly recreate your workspace by reuploading your exported workspace content." [Source](https://www.notion.com/help/export-your-content)
- Third-party export analyses add detail: views, filters, relations, rollups, formulas, comments, and page history are dropped; a relation collapses into the plain title text (or raw page ID) of the linked page, and re-importing the CSV yields a dead text column. **[WEAK — vendor blogs, consistent with the official help page]** [Source](https://raccoon.page/blog/notion-export-limitations/) [Source](https://unmarkdown.com/blog/notion-export-broken)
- Synced blocks are true transclusion with edit-anywhere: "If you make a change in one instance of a synced block, that change will also appear in all other places"; one instance is marked ORIGINAL; unsyncing forks the copies into independent blocks. Failure edge: if a synced block has >10 copies, deleting the original removes all copies and Undo won't restore them — identity-sharing has sharp edges even here. [Source](https://www.notion.com/help/synced-blocks)
- Interpretation: Notion proves the .sarib thesis works *when the canonical store is a database of identified blocks and every surface is a live view of it* — and simultaneously proves the cost: the canonical form is proprietary, invisible, and non-exportable. Views being configurations (not derivations with their own existence) is exactly why edit-in-any-view is trivial for Notion and hard for file-based systems.

## 6. Obsidian / Roam / Tana — graph tools: how close to canonical-source-with-projections?

**(a) Canonical:** Obsidian — Markdown files on disk (plus plugin-maintained indexes); Roam — a proprietary block graph with per-block UIDs; Tana — a proprietary node graph ("everything is a node") with supertags as schema. **(b) Edit flow:** Obsidian: edits only in source notes; query results are read-only renders (one sanctioned exception). Roam: block *embeds* are editable anywhere and sync everywhere; block *references* are read-only. Tana: all edits in the app; export is one-way. **(c) Identity loss:** Obsidian queries project from the metadata index only (body prose isn't even addressable); Roam/Tana keep identity internally but lose the live graph at the export boundary. **(d) Verdict:** the outliner tools re-derive Notion's answer (IDs everywhere, editable transclusion) at block granularity; the file-based tool keeps projections read-only because Markdown has no block identity to write back through.

- Obsidian Dataview, from its own docs: "Dataview is a live index and query engine over your personal knowledge base"; and the crucial boundary statement: "Dataview is meant for displaying and calculating data. It is not meant to edit your notes/metadata and will always leave them untouched (... except if you're checking a Task through Dataview.)" A rendered table is a projection you cannot edit — with exactly one carefully-scoped writeback (task checkboxes), which works because tasks are discrete list items the index can locate in the source file. [Source](https://blacksmithgu.github.io/obsidian-dataview/)
- Dataview also documents the projection's blindness: "Only indexed data is available in a Dataview query" — the poem body in its own example is not queryable, only frontmatter/inline fields/tags/list items. The projection sees schema-ish metadata, not the knowledge itself. [Source](https://blacksmithgu.github.io/obsidian-dataview/)
- Roam distinguishes references from embeds: a block reference is read-only ("you cannot change the content of a block reference"), while with block embeds "you can change the content of any embed blocks and all blocks derived from one original block will be synchronized" — editable transclusion keyed on block UID. **[WEAK — description from the roam-block project README (an Emacs reimplementation describing Roam's behavior) and community docs; Roam's own reference docs are app-internal]** [Source](https://github.com/Kinneyzhang/roam-block) [Source](https://x.com/roamresearch/status/1260350131544576000)
- Tana: "In Tana, everything is a node: The fields, the views, the commands, the settings... everything," and supertags make "the content... the tag" — tagging a node instantiates a schema with typed fields on that node. Schema lives in the graph, not in a sidecar. [Source](https://outliner.tana.inc/learn/features/supertags) [Source](https://outliner.tana.inc/articles/intro-to-nodes-fields-and-supertags)
- Tana's export tells the round-trip story in one line: the JSON export is "a full-fidelity export of data related to your graph," but "for technical reasons, there is currently no way for users to import these files back into Tana." Full-fidelity out, zero-fidelity back — even the vendor's own format doesn't round-trip into its own product. [Source](https://tana.inc/docs/copy-paste-and-export)
- A reviewer's estimate that rebuilding a Tana workspace elsewhere loses "roughly 40 percent of the structure" (field definitions, type hierarchies, query results don't translate to Markdown/JSON cleanly) — **[WEAK — single review, unverifiable number; treat as illustrative only]** [Source](https://www.xda-developers.com/tana-supertags-review/)
- Interpretation: the trade is stark. Obsidian keeps a human-ownable plain-text canonical form and pays with read-only projections (no block identity to address). Roam/Tana get editable projections and pay with a proprietary canonical form that exits only as a corpse. Nobody in this category has both.

## 7. Pandoc — the universal converter's honest confession

**(a) Canonical:** nothing — Pandoc deliberately has no canonical document; its AST is a *transit* representation (readers → AST → writers, with filters over the AST). **(b) Edit flow:** one-way per conversion; round-trips are compositions of lossy maps. **(c) Identity loss:** the AST is intentionally less expressive than most formats it connects — structure is kept, formatting detail and format-idiosyncratic constructs are dropped or shoehorned (attributes forced into wrapper Divs/Spans). **(d) Verdict:** round-trip is explicitly a non-goal, stated in the manual's second section.

- The manual's own words: "Because pandoc's intermediate representation of a document is less expressive than many of the formats it converts between, one should not expect perfect conversions between every format and every other. Pandoc attempts to preserve the structural elements of a document, but not formatting details such as margin size... While conversions from pandoc's Markdown to all formats aspire to be perfect, conversions from formats more expressive than pandoc's Markdown can be expected to be lossy." [Source](https://pandoc.org/MANUAL.html) (same text in the hosted section page: [Source](https://pandoc.org/demo/example33/2-description.html))
- Note the asymmetry Pandoc claims: lossless *outbound* from its home dialect (pandoc Markdown ≈ a serialization of the AST), lossy *inbound* from anything richer. The interlingua defines a fidelity ceiling; everything richer gets clipped to it.
- AST design constraints (Pandoc API docs): the hard Block/Inline type distinction makes some real documents unrepresentable (e.g., a link whose text is a block quote), and because attributes cannot attach directly to paragraphs or text, docx paragraph/character styles force synthetic Div and Span wrappers to hold them. [Source](https://pandoc.org/using-the-pandoc-api.html)
- Concrete round-trip defect class: markdown → AST/JSON → markdown can change meaning at the token level, e.g., escaped ATX-header syntax re-emerging as a real header (issue #7726). Even structure-preserving pipelines corrupt at the edges where escaping/serialization decisions aren't invertible. [Source](https://github.com/jgm/pandoc/issues/7726)
- Interpretation: Pandoc is the strongest evidence that "one interlingua for all formats" forces lowest-common-denominator semantics. Its success comes from *embracing* lossiness (structure over fidelity) rather than fighting it — and from making its own Markdown the privileged dialect that maps 1:1 to the AST.

## 8. Headless CMS / structured content — Sanity's Portable Text

**(a) Canonical:** a JSON array of typed blocks stored in the CMS (Portable Text for rich text; arbitrary typed objects for everything else). **(b) Edit flow:** edits happen against the JSON (via the PT editor / API patches); rendering to React/HTML/PDF/Markdown/etc. is one-way through per-type serializers. **(c) Identity loss:** none in storage (`_key` on every block/span); renderers *silently skip* block types they don't recognize — unknown identity is dropped at render time by design. **(d) Verdict:** the canonical-JSON-plus-renderers model holds in production (since 2018); it never claims render-output round-trip — HTML/Markdown → PT requires separate converters and is best-effort.

- The spec: "A Portable Text document is a JSON array of blocks. Each block has a `_type`"; text blocks carry `children` (spans), `style`, `markDefs`, list metadata; spans carry `text` and `marks`. Status: v0.0.1 Working Draft, "stable in practice since 2018," used in production by Sanity, Hugo, and others. [Source](https://www.portabletext.org/specification/)
- Why JSON rather than the render formats: "HTML and Markdown encode rendering assumptions into the content. Portable Text separates content structure from presentation, making the same content renderable as React components, HTML strings, PDFs, or plain text." [Source](https://www.portabletext.org/specification/)
- Identity is a first-class design decision: "Why `_key` on blocks? Keys enable real-time collaboration. When two editors modify the same document, keys let the system identify which block changed without relying on array position." Position-independent identity is what makes concurrent edits mergeable. [Source](https://www.portabletext.org/specification/)
- Shared-annotation identity: `markDefs` (annotation data, keyed) are separate from `marks` (references on spans), "so multiple spans can share the same annotation data without duplication" — the link is one object referenced by many spans, not N copies. [Source](https://www.portabletext.org/specification/)
- The lossiness valve: "Renderers that don't recognize a custom block type skip it gracefully." Projection tolerance is achieved by *dropping* unknown content silently — good for uptime, bad for fidelity guarantees; a projection can quietly be a subset of the source. [Source](https://www.portabletext.org/specification/)
- Sanity's framing: Portable Text is "an agnostic abstraction of rich text that can be serialized into pretty much any markup language, be it HTML, Markdown, SSML, XML." Inbound conversion from HTML/Markdown exists as separate tooling, not as a guaranteed inverse. [Source](https://www.sanity.io/guides/introduction-to-portable-text) [Source](https://www.portabletext.org/conversion/html-to-portable-text/)
- Interpretation: structured content is Notion's model with the walls removed — open spec, exportable JSON, bring-your-own renderer — but it gives up the editing surface (you need a schema and an editor build) and it round-trips only at the JSON layer, never through the rendered artifacts.

## Cross-system pattern check

The hypothesis to test was: **round-trip dies where projections drop identity, or where two representations both accept human edits.** The evidence supports it, with one refinement.

| System | Projection carries identity? | How many representations accept edits? | Round-trip outcome |
|---|---|---|---|
| XSLT output | No | 1 (source) | None attempted; one-way held in publishing |
| Org prose export | No | 1 | None; nobody expects it |
| Org tangle w/ `:comments` | Yes (comment links) | 2 | Works (detangle), fragile — in-band anchors break |
| Knuth WEB | Irrelevant (outputs write-only) | 1 | Consistent by construction; adoption failed |
| Raw ipynb + git | Weak (position + volatile metadata) | 2+ (every collaborator/kernel) | Catastrophic (invalid JSON conflicts) |
| jupytext pairing | Partitioned (text=inputs, ipynb=outputs) | 2, with single owner per state class | Works until both edited between syncs → manual pick |
| Notion internal | Yes (block UUIDs; properties survive type change) | N views of one store | Works — the closest living realization |
| Notion export | No (IDs, relations, views dropped) | — | Officially non-reimportable |
| Roam embeds | Yes (block UID) | N embeds of one block | Works (edit-anywhere transclusion) |
| Obsidian Dataview | No (index only, no block IDs) | 1 (source files) | Read-only projections, one scoped writeback (tasks) |
| Tana | Yes internally; JSON export keeps data | 1 (app) | Full-fidelity export, no importer — one-way even to itself |
| Pandoc | No (AST is transit, not anchor) | — | Explicit non-goal; lossy by documented design |
| Portable Text | Yes (`_key` per block/span) | N editors on one JSON | Holds at JSON layer; renders are terminal |

Refinement: it isn't just *identity* — it's identity **plus a single owner per class of state**. Jupyter breaks even with identity-ish matching because inputs, outputs, and environment metadata (different owners, different volatility) share one file. Jupytext fixes it not by adding IDs but by assigning each state class one authoritative representation.

## Design lessons for .sarib

1. **Give every knowledge atom a stable, position-independent ID, and make every projection carry it.** Portable Text added `_key` specifically so "keys let the system identify which block changed without relying on array position" ([spec](https://www.portabletext.org/specification/)); Notion's UUID-per-block is why edit-in-any-view works ([Notion blog](https://www.notion.com/blog/data-model-behind-notion)); org-babel-detangle only round-trips when tangled files embed link anchors ([Org manual](https://orgmode.org/manual/Extracting-Source-Code.html)). A projection without source IDs is a dead end by construction — this is *the* precondition for edits flowing back.

2. **Separate state by owner and volatility; never store human-authored, machine-derived, and environment state in one unit.** The entire Jupyter+git disaster reduces to execution counts, output blobs, and kernel metadata cohabiting with source in one JSON file ([fast.ai](https://www.fast.ai/posts/2022-08-25-jupyter-git.html)); every fix that worked (nbdev save hook, jupytext pairing) partitions ownership ([jupytext](https://github.com/mwouts/jupytext)). In .sarib: content, derived/cache, and session state must be separable layers with one authoritative writer each.

3. **Views should be configurations over the canonical store, not exported artifacts.** Notion's table/board/timeline are saved configurations on one data source, so an edit in any view is an edit to the record ([views help](https://www.notion.com/help/views-filters-and-sorts)); the moment content crosses into a derived artifact (Markdown/CSV export), Notion itself concedes "you can't instantly recreate your workspace by reuploading" ([export help](https://www.notion.com/help/export-your-content)). Corollary: if .sarib wants writable views, they must be windows, not copies.

4. **If a projection must be one-way, make it explicitly terminal and never let humans edit it — consistency by construction beats reconciliation.** Knuth's TANGLE deliberately scrambled its output so nobody would edit it, and weave/tangle stayed consistent because they ran "on the same source" ([Wikipedia/Knuth](https://en.wikipedia.org/wiki/Literate_programming)); XSLT pipelines survive to this day in DITA-OT precisely where the one-way contract is honest ([DITA-OT architecture](https://www.dita-ot.org/dev/reference/architecture.html)). The fatal zone is the ambiguous middle: an output that looks editable but has no back channel (Jupyter's ipynb in git, Notion's exports).

5. **Don't build the canonical model as a lowest-common-denominator interlingua; pick one privileged dialect that maps 1:1 to the model.** Pandoc's manual admits "one should not expect perfect conversions" because its AST is "less expressive than many of the formats it converts between," while conversions *from pandoc's own Markdown* "aspire to be perfect" ([Pandoc manual](https://pandoc.org/MANUAL.html)). Lesson: .sarib's text syntax should be a lossless serialization of the .sarib model (like pandoc-Markdown↔AST or Tana's full-fidelity JSON), and fidelity claims for foreign formats should be explicitly bounded.

6. **A plain-text canonical form and writable projections are in tension; .sarib's differentiator is resolving it — with in-band identity as the known-fragile compromise.** File-based Obsidian keeps ownable text but its query projections are read-only ("Dataview... is not meant to edit your notes" — [Dataview docs](https://blacksmithgu.github.io/obsidian-dataview/)); database-based Roam/Tana/Notion get editable transclusion but their canonical form is proprietary and exits lossy or non-reimportable ([Tana export docs](https://tana.inc/docs/copy-paste-and-export)). Org's detangle shows in-band anchors (comments/markers in the text) can carry identity through plain text, and also shows they break when content collides with anchor syntax ([bug report](https://list.orgmode.org/orgmode/87jysrbejg.fsf@bhw-yoga.localdomain/)). Design the anchor syntax to be collision-proof and escapable from day one.

7. **Preserve invisible state through transformations — "turn into" must never destroy properties the target view doesn't display.** Notion keeps a to-do's checked state through Heading → Callout → back-to-to-do because type change touches only the type attribute; they name the principle: "we preserve as much user intention as possible" ([Notion blog](https://www.notion.com/blog/data-model-behind-notion)). Portable Text's inverse warning: renderers that "skip gracefully" unknown types silently subset the content ([spec](https://www.portabletext.org/specification/)). .sarib rule: projections may *hide* fields, never *drop* them; and any lossy render must be declared, not graceful-silent.

8. **Round-trip capability doesn't sell itself — the projection people live in must be first-class, or the system loses to worse-but-comfortable tools.** Knuth called literate programming "the most important thing that came out of the TeX project" ([2008 interview](https://www.informit.com/articles/article.aspx?p=1193856)) and it still lost, partly because compilers/debuggers/colleagues all lived in the tangled projection and the method demanded authors be storytellers ([LiterateCS intro](https://johtela.github.io/LiterateCS/Introduction.html)); XSLT's model was sound and its authoring experience made it "a niche programming language" at best ([Cook + comments](https://www.johndcook.com/blog/2009/03/16/what-happened-to-xslt/)). For .sarib: the canonical format must itself be pleasant to read and write raw, because some critical tool in the ecosystem will always address it directly.
